### 1. Introduction
 

HakoSpace is self-hosted software. This Privacy Policy describes how the **HakoSpace software itself** handles data. It does not govern any specific hosted instance, because we do not run any HakoSpace chat server instance. What HakoSpace does operate is: the official website and software release source; the opt-in anonymous Improvement Program (telemetry); license verification for commercial editions (not yet offered); the HakoSpace Official Account (which has its own Terms of Service and Privacy Policy and is outside this Policy); and an opt-in public server directory, hakoHub (Section 4A).
 

When you deploy HakoSpace, you are the one in control. Apart from the information involved in features you choose to turn on (the Improvement Program and hakoHub; see Sections 4 and 4A), the HakoSpace development team has no visibility into your server, your users, or your data.
   

### 2. Self-Hosted Architecture
 

This is the most important thing to understand about HakoSpace:
  

We cannot access your data. Not because of policy, but because of architecture.
  
 
- HakoSpace runs entirely on infrastructure you control 
- The HakoSpace development team has no access to any data stored on self-hosted instances (once you voluntarily turn on hakoHub, HakoSpace reads the directory information that server chooses to make public, see Section 4A; this is not access to stored data) 
- We cannot read, monitor, or retrieve messages, files, user accounts, or any other data from your server 
- Each server instance is fully independent and isolated from every other instance 
- HakoSpace operates no central cloud service or shared database that carries chat content, and by default the software sends no telemetry or other server data to HakoSpace (the desktop application does, by default, connect to HakoSpace's software release source to check for updates; see Sections 4 and 6). The central services HakoSpace operates are limited to those listed in Section 1, of which telemetry and the directory must be turned on by a server administrator 
 

Your server is yours. We have no way in; the only service that connects to a server is the hakoHub directory service: once you choose to turn hakoHub on and register, it periodically reads the directory information that server chooses to make public (Section 4A), which contains no messages, files or user accounts. In addition, when anyone submits a server address for registration with an Official Account, the directory service sends one verification request to that address's hub endpoint, whether or not the server has turned hakoHub on; if verification fails, no data about that server is kept.
   

### 3. Data Stored by the Software
 

HakoSpace stores the following data locally on the server operator's infrastructure:
 
 
- **User accounts**: username, display name, password hash (bcrypt), avatar image 
- **Messages and attachments**: all chat messages and uploaded files sent by users 
- **Voice/video metadata**: call records (who called whom, when, and for how long) stored in the local database. This metadata includes participant user IDs, session start/end timestamps, and channel identifiers — it does *not* include any audio, video, or screen-share content. 
- **Server configuration**: settings, roles, permissions, channel structure 
- **Audit logs**: moderation actions and administrative events, including the IP address of the person who performed the action (stored on the operator's server and not sent to HakoSpace) 
- **Server logs and IP ban list**: the server log (`hako.log` in the data directory, kept for up to 30 days under the default rotation settings; in container deployments the same output also goes to the container log, kept as the operator configures) records the user ID and IP address of voice connections; IP addresses that trip rate limits are automatically added to the IP ban list, and the record is kept after the ban expires. All of this is stored on the operator's server and is not sent to HakoSpace. For the consent record stored when a user accepts the EULA and this Policy, see Appendix A.2. 
- **AI usage records**: when the operator enables AI features, the software records, for each use, the member, the time, the provider, the model, the token counts, the cost (when OpenRouter is used), and whether it succeeded or why it failed. It **does not record the content of the messages a member sends to the AI** (a direct message itself is stored like any other message). Tool calls the AI performs are recorded with their parameters and results. Per-call records are kept for 30 to 365 days depending on the server setting (default 90 days); daily aggregate figures are kept. 
 

#### 3.1 Real-Time Media Data Flow (Camera, Microphone, Screen Share)
 

When a user activates their camera, microphone, or screen share, the corresponding media stream follows a **relay-only path** through the server:
 
 
- **Capture**: The browser or desktop client captures frames from the device (via `getUserMedia` or `getDisplayMedia`). Capture occurs entirely on the participant's device; no frames leave the device until transmission begins. 
- **Encoding & Transmission**: Frames are encoded (VP8 / VP9 / H.264) and transmitted over an encrypted WebRTC connection (DTLS-SRTP) to the HakoSpace server instance. 
- **Relay (SFU)**: The server acts as a Selective Forwarding Unit. Incoming media packets are forwarded to other participants who have subscribed to the stream. The server **does not decode, transcode, inspect the contents of, or persist** media packets. Packets reside in in-memory buffers only for the milliseconds required to forward them. 
- **Playback**: Receiving participants decode the stream client-side and render it for display. 
- **Termination**: When the broadcaster toggles off the camera/microphone/screen, the underlying media track is explicitly stopped (`track.stop()`), which releases the hardware and extinguishes the operating-system camera / microphone indicator. No frames captured during the session are retained by the software. 
  

The unmodified HakoSpace software writes zero camera, microphone, or screen-share frames to disk. The SFU is a stateless relay with respect to media content.
  

**What *is* persisted**: call metadata (who joined, when, duration) and privacy-chip signal logs for abuse-response purposes; these contain no media frames. **What is *not* persisted**: audio samples, video frames, screen-share content, or any derivative (thumbnail, still, transcript) of them.
 

**Device-level permission**: The software respects the operating system and browser permission model. Camera and microphone access require an explicit user grant (browser prompt, or OS-level TCC on macOS, or Windows Privacy Settings). Denying or revoking permission at the OS or browser level disables the corresponding feature in the software; no workaround is present in the software.
 

**HakoSpace does not and will not introduce in-product recording capabilities within the current major release line.** This commitment mirrors EULA §11.2 and reflects HakoSpace's architectural and product intent: the software exists as a relay for ephemeral communication, not as a retention platform for user media.
 

**Operator-enabled recording, if any**: A server operator may, at their own legal risk and responsibility, install or configure external recording infrastructure that captures relayed media *outside* the unmodified HakoSpace software. Such recording is **not** part of the software, requires affirmative operator configuration of third-party tooling, and obligates the operator (not HakoSpace) to comply with applicable recording-consent laws for every participant. See the EULA §11.2 for the corresponding license terms.
 

All of this data lives in a local SQLite database file and local file storage on the operator's machine. None of it is transmitted to HakoSpace.

### 4A. Public Server Directory (hakoHub)
 

hakoHub is a public directory of HakoSpace servers operated by HakoSpace (hub.hakospace.com). It is **opt-in**: off by default and independent of the Improvement Program in Section 4.
 

#### 4A.1 Who can turn it on, and how
 

Only a server administrator with the `manage_system` permission can, on the "Make my server public" page in hakoApp, turn hakoHub on, generate a hub key, write the directory description, and switch the two count statistics on or off individually. To be listed in the directory, the administrator (or someone they have authorized) must also register the server with a HakoSpace Official Account at auth.hakospace.com/hub and agree to the Official Account Terms of Service and the hakoHub Listing Policy. The administrator can at any time disable publishing, regenerate the key (the old Listing is withdrawn once HakoSpace's probe confirms it), or withdraw the Listing in the Official Account.
 

#### 4A.2 What HakoSpace reads
 

Once turned on and listed, HakoSpace reads: the server address, name, directory description, icon URL (only the URL is read and no image is stored; visitors' browsers load the image directly from your server; when review staff view a Listing on the review page (both the approved icon and a pending new icon), HakoSpace downloads the icon from your server solely to show it on the review page and does not store the image), how to join (registration mode), a member-count range and an online-count range (each read only if you choose to publish it), the hakoApp version and the protocol version (always read, never shown publicly), and the host name your server reports having received (for review staff reference only, not shown publicly). Counts are provided **only as ranges** (0, 1–4, 5–19, 20–99, 100+): member counts exclude bots, banned accounts and unverified accounts, and online counts exclude invisible users and AI bots; the member count is published by default and the online count is off by default.
 

HakoSpace **does not** read messages, files, channels, member lists or members' personal data, and does not obtain exact counts.
 

#### 4A.3 How it is read
 

The direction is from HakoSpace to your server; **hakoApp does not connect to HakoSpace on its own** to notify or upload directory information. HakoSpace's directory service periodically (currently about every 30 minutes; about once a day for hidden Listings) sends a request to your server's hub endpoint, looking up the domain's DNS before each connection. The request carries your registered address, a timestamp, a random value, the Listing's current directory status (pending, listed, or hidden, with a reason category) and a signature computed with the hub key, and hakoApp records that status and shows it on its admin page; the request and the normal response are both signed with the hub key, and the probe carries only signatures, never the key itself (when you register or change the address, you submit the hub key once to the Official Account service over an encrypted connection). A full probe is made at the moment of registration, and at registration and when the icon changes, a header-only request checks the icon's type and size; a request with an incorrect signature gets no name, description, count or other directory information (it only learns that the endpoint is "not enabled" or "authentication required", or receives the public fingerprint of your hub key). Your server will see these connections and may record them in its own logs. An administrator can switch the endpoint off entirely with the environment variable `HAKO_HUB=off`.
 

#### 4A.4 How HakoSpace handles it, and for how long
 

HakoSpace stores the data it reads, the address and tags you submit, the hub key's public fingerprint and an encrypted probe key derived from the hub key (the hub key itself is not kept), probe status, the registrant's Official Account identifier and consent record, and review and notification records, and shows approved directory information publicly. This data belongs to the HakoSpace Official Account service; how it is handled and how long it is kept (including a 90-day tombstone after withdrawal, and the block list) are set out in Sections 9 and 11 of the *HakoSpace Official Account Privacy Policy*, and your rights and how to exercise them in its Section 12, not in the rest of this Policy. For withdrawal, see 4A.1.
 

#### 4A.5 Review and take-down
 

A first Listing and changes to the name, description, icon, tags and server address are subject to HakoSpace review; under the hakoHub Listing Policy, HakoSpace may hide or take down a Listing and, for serious or repeated breaches, block a domain name or hub key fingerprint. Review covers only the data shown in the directory, not the server itself or the content on it (EULA §11.7).
 

#### 4A.6 Your users
 

The directory publishes server-level information and count ranges, and no data about any individual user. We recommend (but do not require) that operators tell the users of their server before making it public in the directory; hakoApp's "Make my server public" page will carry the same reminder.

### A. Legal Consent Enforcement
 

HakoSpace uses a **server-side legal consent gate** to ensure that every user of a HakoSpace server instance has actively accepted the "most recent version requiring consent" of the EULA and this Privacy Policy, or any later version (see A.1 and A.3), before using any feature that processes personal data.
 

#### A.1 Versioning
 

Each of the EULA and this Privacy Policy is identified by an independent **effective date** in ISO format (`YYYY-MM-DD`), displayed in the document header (e.g., **Privacy Policy effective 2026-10-16**). Any of the following is a material change: expansion of collected data categories, change of retention period, introduction of new third-party processors, new feature categories (noting that, per §3.1 and EULA §11.2, HakoSpace commits not to introduce in-product recording within the current major release line), or any other change that would, in HakoSpace's good-faith assessment, affect a reasonable user's decision to use the service.
 

Any change to the wording, including editorial changes (typo fixes, phrasing cleanup, link corrections, clarifications that do not change the meaning), is **never applied in place** to a published version; it is published as a new version (a new effective date, or, if another version must be issued on the same day, a suffix, e.g., `2026-09-26-a`), and the earlier version stays unchanged. New versions are of two kinds: a **material-change version** (any of the situations in the previous paragraph) **requires re-consent**; an **editorial version** (editorial changes) **does not require re-consent**. The software records the "current version" and the "most recent version requiring consent" separately, and only the latter is used by the consent gate (see A.3).
 

#### A.2 Account-Level Acceptance Record
 

Your account on a given server instance stores four values: the EULA version you last accepted, the Privacy Policy version you last accepted, and the UTC timestamps of each acceptance. These values constitute personal data and are processed solely for the purpose of operating the consent gate and providing evidence of your acceptance. In addition, each time you accept, the server stores a separate consent record of the versions and time, your IP address, User-Agent, the source label sent by the client and the server version, kept permanently as evidence of acceptance.
 

#### A.3 Server-Side Gate
 

At each session start (HTTP API request or WebSocket HELLO), the server compares your recorded acceptance versions against the "most recent version requiring consent". You are treated as having consented if the version you accepted is not earlier than that version (and not later than the current version), so an editorial version does not stop you. If your recorded version of either document is earlier than the most recent version requiring consent, later than the current version (for example, after the server is rolled back), malformed, or empty, the server refuses the request with an error (`LEGAL_CONSENT_REQUIRED`) and returns the list of documents requiring re-acceptance together with the current version strings.
 

The client, upon receiving this error, must display a **blocking modal** containing the full text of each document requiring re-acceptance. The modal has no dismissal path other than accepting or leaving the service. Each document requiring re-acceptance has its own checkbox ("I have read and agree to the EULA" / "I have read and agree to the Privacy Policy"), which can be checked only after that document has been scrolled to the bottom in its full-text viewer; the Accept button is enabled once every document requiring re-acceptance this time has been checked; a document that does not require re-acceptance is not shown and need not be checked. Upon acceptance, the client POSTs the accepted version strings to the server, which updates only the version and time fields of the document(s) requiring re-acceptance (the record of the other document is left unchanged) and grants access.
 

#### A.4 Applies to All Users, Not Only New Ones
 

On the release day that introduces a new material-change EULA or Privacy Policy version, **all existing users** (not only newly-registered ones) will see their next connection intercepted by the re-consent modal. This design reflects that (i) a material change in collected data categories or processing purposes affects existing users equally, and (ii) GDPR and equivalent frameworks require affirmative, informed consent for the new purpose — passive continuation of use does not constitute such consent.
 

Server operators migrating to a new version therefore must expect temporary access friction for their users on release day; this is a feature of the consent framework, not a bug.
 

#### A.5 Decline Consequences
 

If you decline the new version, you will be unable to use that server instance until you accept. Your existing account data is not deleted by the decline; you may return and accept at any later time. You retain the right to request deletion of your personal data under §7 / §8 below, independently of the consent decision.
 

#### A.6 Historical Versions
 

Each published version of this Privacy Policy and the EULA remains accessible at a stable archive URL (typically `/legal/archive/<YYYY-MM-DD>/privacy` and `/legal/archive/<YYYY-MM-DD>/eula`), so that you may always review the exact text you accepted.
